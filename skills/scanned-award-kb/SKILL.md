# 批量扫描件公文 → 结构化知识库

## 一、适用与边界

**适用**：一个目录里放着同一批同类公文，文书具有**多副本结构**（一式多联、正副本、多标段同格式）或**成对结构**（中标通知书 + 未中标通知书）。典型：中标通知书（第一至第四联）、成交通知书、评标结果公示、定标报告、未中标通知书。

源文件分两条路线，**开工第一步就要判**：

| 形态 | 判据 | 路线 |
|---|---|---|
| 纯扫描件 | 页均字符数 `< 100`，页面只有整版位图 | OCR 路线（步骤 2 至 5），签章只能靠图 |
| 带文本层的电子公文 | 页均字符数 `> 200` 且文本干净无乱码 | **直取路线**，跳过 OCR，改做签章三层取证（步骤 4B） |

**判错代价**：对带文本层的电子公文盲目跑 OCR，会把干净文本层降级成一堆识别错误，纯属倒退。反之，把扫描件当电子公文，`get_text()` 返回空串，白跑一轮。用一条命令判：`[len(p.get_text().strip()) for p in fitz.open(f)]`。

**边界**（不要与下列技能混用）：

| 源文件形态 | 应调技能 |
|---|---|
| 有文本层但被 OCR 损坏（形近字、数字漏位） | `cn-gov-eng-pdf-vectorkb` |
| 工程批复 + 投资概算表，需逐行重建与勾稽 | `gongwen-pifu-kb` |
| 以图像为主、文字为辅的图册/案例集 | `image-pdf-to-kb-site` |
| PDF 与 Word 双源需互相校对 | `pdf-word-dual-source-rag` |
| 纯扫描件或带文本层电子公文 + 需建台账与站点（本技能） | 本技能 |

## 二、五层产出结构

```
<主题>-知识库/
├── index.html              站点层：单文件离线，侧栏导航 + 全文检索 + 台账 + 条形图
├── README.md               索引层：结论速览、取数指引、待核清单摘要、复现命令
├── _index.md               索引层：页面索引 + 数据文件结构 + 证据清单
├── wiki/*.md               文档层：总览 1 + 每条目 N + 对照勾稽 1 + 口径方法 1 + 存疑清单 1
├── data/*                  数据层：台账 CSV+JSON、明细 CSV、事实卡、勾稽、核验报告、RAG 条目
├── _build/*                复现层：脚本 + 逐页 OCR 原始结果（含坐标与置信度）+ 版面还原文本
└── _evidence/*.png         证据层：关键字段放大辨读切片，可对照纸质原件复核
```

**先判定"条目"是什么**。本例条目是标段（C02 至 C11），每份 PDF 一个条目。条目数决定文档层页数。

## 三、工作流

### 步骤 1 体检，判定扫描件与结构

```python
d = fitz.open(f)
len(d), [len(p.get_text().strip()) for p in d], [len(p.get_images(full=True)) for p in d]
info = d.extract_image(p.get_images(full=True)[0][0])   # width/height 判 DPI
```

判据：页均字符数 `< 100` 即扫描件，必须走 OCR。扫描图 `2480×3507` 即 A4@300dpi，足以支撑后续放大人工辨读。

**同时统计各文件页数差异**。页数异常的那个文件往往就是结构缺失的那个（本例 8 页 vs 4 页，4 页者缺第三、第四联）。

**页均字符数 `> 200` 则先看文本质量**，用 `page.get_text()` 与 `get_text("dict")` 看有无形近字错乱。干净即走直取路线，跳过步骤 2 至 4，直接落到步骤 4B 做签章取证。

### 步骤 1B 带文本层电子公文的直取路线

上海市建设工程中标／未中标通知书（「上海市建设工程招标投标管理办公室 制」2020 版）是 iText 生成的电子公文，通常**带完整干净文本层**。这类文件用 `get_text("dict")` 逐行取，同时收 `font` 与 `size`，足以还原版面层级（标题 `SimHei 15.8`、正文 `SimHei 11.2`、表栏 `SimHei 9.8`）。

```python
for b in pg.get_text("dict")["blocks"]:
    if b.get("type") != 0: continue
    for l in b["lines"]:
        txt = "".join(s["text"] for s in l["spans"])
        # 记录 bbox / size / font，供后续按 y 排序还原版面
```

**但文本层只覆盖印刷体**。以下内容一律不在文本层内，必须另行取证，漏掉就是漏掉最关键的部分：

| 不在文本层的内容 | 所在位置 |
|---|---|
| 电子印章（红章） | AcroForm 数字签名域的可见外观 |
| 电子签章时间戳 | `Stamp` 注释的外观位图 |
| 手写签名 | 位图或矢量路径 |
| 二维码、页脚小图标 | 页面 `Resources/XObject`（这个 `get_images()` 能抓到） |

**关键陷阱**：前两类**不会出现在 `page.get_images()` 的返回值里**。渲染成图看得见，程序枚举抓不到，因为两者挂在注释的 `/AP` 外观流之下。定位方法：遍历 xref 找 `/Subtype /Image`，或在 `page.get_image_info(xrefs=True)` 结果中留意 `xref` 为 `0` 的条目（`0` 即表示无法从页面资源确定来源，多半来自注释外观）。

### 步骤 2 OCR 并保留坐标

用 RapidOCR（PaddleOCR 模型的 ONNX 版，无需联网下载模型）。**必须保留四角坐标与行置信度**，两者后续都有用。

```python
from rapidocr_onnxruntime import RapidOCR
ocr = RapidOCR()
res, _ = ocr(png)          # res: [[box, text, score], ...]
```

落盘结构：`{文件: [{page, png, w, h, lines: [{x0,y0,x1,y1,cy,txt,score}]}]}`。

### 步骤 3 版面还原（OCR 文本 → 可读表格）

OCR 输出是散行，需还原成行与单元格：

1. 按 `cy` 聚类成行。容差取 `max(14, 0.6 × 相邻两行高度的较小值)`，固定阈值会在字号变化处误拆。
2. 行内按 `x0` 排序，相邻块间距 `< 42px` 时合并为同一单元格，否则以分隔符拼接。
3. 输出 `文件 第N页` + 逐行文本，供低成本通读全局。

**为什么不能省**：把 76 页图像交给视觉模型逐页精读代价过高。版面还原文本让模型用很低的成本掌握全局，再把视觉预算集中在真正需要判定的小块上。

### 步骤 4 字段抽取 + 多副本一致性交叉校验（核心增值）

同一份文书的多个副本（四联、正副本）字段值应当逐字相同。**把这条常识变成自动校验器**：

1. 正则按栏位标签定位取值，跨全部副本汇总，用 `Counter` 聚合。
2. 同一字段出现多个取值即自动标记，进入人工复核队列。
3. 输出「文件 → 存在分歧的字段 → 各取值出现次数」。

本例 10 份文书 120 余个字段中，仅第 2 标出现 2 处分歧（中标价首位 `0` vs `8`、工期末位 `1` vs `4`），其余 9 份四联全同。**这个校验器把复核工作量从"全量核对"压到"只核对报警项"**。

成对结构（中标 + 未中标）的等价做法是**共有栏目聚合**：把两份文书同名栏目取出来比对，分歧即报警。本案 7 项共有栏目逐字相同，两个独立信号一致印证了同一套标段信息。

### 步骤 4B 电子公文的签章三层取证（带文本层电子公文必做）

电子公文的「盖章」以三层落地，互不重叠。**三层都要取，少一层就少一条证据链**。

| 层 | 载体 | 落地形式 | 取证方式 |
|---|---|---|---|
| 印章 | AcroForm 数字签名域 `/FT /Sig` 的 Widget 注释，`/AP` 指向 Form XObject | 红色圆章位图 | 红墨掩膜 + 极坐标展开辨读 |
| 时间戳 | `Stamp` 注释，`/AP` 为一条宽扁位图（如 1100×82） | 日期时刻文本 | 位图 OCR |
| 签名 | 签名对象 `/Type /Sig`，`/Filter /Adobe.PPKLite`，`/SubFilter /adbe.pkcs7.detached` | 证书链 + 声明 + 签名时刻 | PKCS#7 解析 |

**取证书（本案最有价值的一步）**：

```python
from cryptography.hazmat.primitives.serialization import pkcs7
certs = pkcs7.load_der_pkcs7_certificates(der)   # der 由 /Contents 十六进制还原
# 末位证书即签署者：[c for c in certs if c.subject.rfc4514_string().startswith("CN=<招标人>")]
```

解出的签署者证书 `CN` 与 `O` 字段即**招标人法定名称**，属证书级证据，比印章辨读硬得多。本案正是靠它，才敢判定那份**没有印刷体招标人名称、也没有印刷体日期**的未中标通知书。

**三个必须记住的技术点**：

1. `/Reason`（签署声明）**以十六进制编码的 UTF-16BE 存放**，不能直接当 ASCII 读：
   ```python
   bytes.fromhex(h).decode("utf-16-be").lstrip("\ufeff")   # 带 BOM，须 lstrip
   ```
   本案解码得「我同意签署该文件，并承认数字签名的法律效力。」
2. `/M`（签名时刻）与签章时间戳位图 OCR 构成**两条独立路径**，可互证。本案两处逐秒吻合（09:38:43 / 09:39:29）。
3. **印章位图的有效分辨率由签名域尺寸决定，往往很低**。本案 `/Rect` 为 123.06 pt 见方，内置位图仅 207×207 像素，折合约 125 dpi。指望放大到 1200 dpi 读到更多细节是徒劳，**信息上限在源位图**。环带半径必须靠径向红墨密度直方图定（本案文字带 `r ∈ [28, 52]`、外框 `r ∈ [54, 67]`）。

**展开图的两个硬要求**（本案实测踩坑）：

- **必须做四取向比对** `flipud × fliplr`。极坐标展开后文字方向取决于径向索引方向，本案只有垂直翻转版可读，不翻转则通篇是镜像字。
- **宽度控制在 1100 至 1600 px**。本案 6048×270 的整环展开图被渲染端压缩到完全不可辨，改 1500×300 才可读。

**印章与文件同源判定**：把两份文件的印章位图直接 `numpy.array_equal` 比对。本案结果逐像素相同，即加盖同一枚电子印章，且两次签章相差 46 秒，与「先定标、后告知落选人」的次序吻合。

**免责纪律**：证书解析只说明文件内部结构与外观所载信息，**不等于完成了签名密码学验证**。未做证书链信任锚校验、未验证 `ByteRange` 摘要与签名值的密码学一致性、未查吊销状态。交付物中必须写明这一边界，并指向文书自带的官方验证渠道（本案为附注载明的上海市建筑业官方微信二维码）。

### 步骤 4C 未中标通知书的固有三处形态特征

处理未中标通知书（「上海市建设工程材料/设备未中标通知书」）时，以下三处**是原件本来就如此，不是转录缺失**，须作为「原件特征」记录，不可当作数据缺陷或静默补全：

1. **无具名收件人**。标题下直接进正文，正文以「贵公司」代称，未中标人只在附表列示。若需分别送达各家，各份须另行标识收件人。
2. **无印刷体日期**。日期唯一来源是电子签章时间戳，取值时须标注来源，不得冒充印刷体。
3. **招标人名称仅在印章内**。「招标人（盖章）：」栏无印刷体名称，必须走步骤 4B 的证书路径取得独立印证。

另需留意文书名称措辞差异：中标通知书为「建设工程**材料采购**中标通知书」，未中标通知书为「建设工程**材料/设备**未中标通知书」，前者无「/设备」字样。照录，不统一。

### 步骤 5 关键字段的窄条纵向拼接复核法

视觉复核的瓶颈是图像数量。解法是把 N 份文书的**同一字段行**裁出来纵向摞成一张长卷，一次读全：

```python
# 每个条目裁同一 y 带、同一 x 区间，纵向拼接
bands = [(base, im.crop((x0, y0, x1, y1))) for ...]
# 拼接后统一缩放，宽度控制在 1100 至 1600 px，避免渲染时被压缩到看不清小字号
```

要点：
- **宽度控制在 1100 至 1600 px**。超过会被渲染端压缩，小字号数字（注册号、金额小数位）会糊掉。
- **高度不要堆太多条**。总高超过约 3000 px 会被压缩；改成分 2 至 3 张。
- 相邻字段行可合并成一图（如"中标价+工期"一行、"建造师+专业+注册号"一行），条目数翻倍读取效率。
- 列宽紧张时只裁值所在区间，但要保住栏位标签以防错位。

本例用 4 张 `KEY_*.png` 读完全部 10 个条目的中标价、工期、建造师、注册专业；2 张 `Z3_*.png` 读完注册号；5 张 `M_*.png` 读完备注栏；4 张 `DATE_*.png` 读完签章日期。

### 步骤 6 印章辨读（名称只在印里时）

公文常在「（盖章）」处只盖章不印名称。红章辨读三步：

1. **定位**：红色像素掩膜 `(R>110) & (R-G>32) & (R-B>32)`，排除黑色正文与手写日期。
2. **择优**：同一枚章在 N 页反复盖印，油墨深浅不同。**逐页统计红墨像素数取最大者**，比修图更有效。
3. **读圆章文字**：最小二乘拟合外圈圆心（Kasa 法迭代精修，仅用 `R±14` 环带像素），再做极坐标展开。
   - **关键：文字环带靠径向红墨密度直方图确定**，不要凭猜。实测文字在 `r ∈ [70,122]`，外框在 `r ≈ 126~136`。换一批印章量级会变（电子印章小得多，实测文字带 `r ∈ [28,52]`、外框 `r ∈ [54,67]`），一律以直方图实测为准。
   - 圆章底部通常留白，文字自 8 点钟方向顺时针起笔。展开后先按角度切成 3 段分别放大辨读，再按起笔方向拼回。
   - 展开图上下左右四个方向各生成一份，挑可读的那份。**极坐标展开的方向不能想当然**，必须四取向比对后取可读者。
   - 输出宽度压在 1100 至 1600 px。实测整环展开 6048×270 被渲染端压缩到完全不可辨，改 1500×300 才可读。
   - 直接裁剪放大（4 倍）在文字倾斜不离谱时也有效，可作交叉验证。
4. **方章（个人名章）**：多为 2 至 3 字，按印面版式定序。**版式推断属推定，必须标注**，不可当作原文事实。

**纪律**：印章是间接取证。名称读出来后要在正文显式写明来源「取自印章印文，栏面无印刷体可对照」，并进存疑清单。

### 步骤 7 易混字符的定量判读

`0/8`、`1/4`、`1/7` 在低质扫描中最易混。不要只靠肉眼，加一层量化：

1. **中线墨迹段数**：取字形垂直中线扫描行，统计墨迹连通段数。`0` 为 2 段（左右两竖），`8` 在交叉处为 3 段。
2. **腰部收窄比**：中段最大宽度 / 上段最大宽度。`0` 接近 1.0（饱满椭圆），`8` 明显小于 1（两环交接处收腰）。
3. **同行 OCR 置信度对比**：同一字段在不同副本上的行置信度差异，直接指示哪份成像更差。
4. **字形比对廊**：把争议字符与同页已知的 `0`、已知的 `8` 并排同倍放大，对比结构特征。

若量化结果仍分歧，**判为存疑项并记录双方取值与判据**，不强行推定。本例第 2 标的中标价首位即如此处理，取高置信度副本的值，同时把第一联读数列入存疑清单第 1 项。

### 步骤 8 双向核验

**正向**（交付值 → 源文本）：凡标为「原文直取」的字段，其值必须能在源 OCR 文本中找到字面出处。

- 源文本做**去全部空白**归一，因为 OCR 逐行输出而字段常跨行书写（注册号、长专业名）。
- 但绝不能只做去空白就完事：去空白会让相邻单元格首尾相接产生**伪数值**。实测「高度 4. 2」与「面积 250」相接成 `4.2250`。伪数值须识别并排除，不可误判为漏收。
- 分行书写的字段（如注册号：省份简称单独一行 + 数字主体一行 + 末位换行）应拆段分别核对。

**反向**（源文本 → 交付值）：源文本中每个含 2 至 4 位小数的数值，都应在交付物中有对应条目。未收入的必须逐项定性。

**反向核验必须先按数值性质分类**，否则满屏假阳性。交付物里的数字分两类：

| 类别 | 例子 | 溯源对象 |
|---|---|---|
| 内容类 | 金额、工程量、证号、日期 | **文书文本层**，必须字面可查 |
| 取证类 | 签名域 `Rect` 坐标、PDF 版本、iText 版本、证书有效期、位图尺寸、OCR 置信度 | **PDF 对象路径**，逐条登记在取证表中，不参与内容溯源 |

本案首次反向核验未做分类，报出 18 项「未溯源」，全部是 `128.37`、`251.43` 这类签名域坐标与 `5.5`、`2.1`、`1.4` 这类工具版本号。分类后内容类未溯源降为 0 项。**判据**：凡来自 PDF 结构而非文书正文、表格的数值，一律归取证类，并在交付物中写明其来源为对象路径。

**两个高频陷阱**：
- 格式化精度：`"%g" % 66322.4423` 得 `66322.4`（默认 6 位有效数字）。核验比对必须用完整精度，否则全是假阳性。
- 整数值比对：交付用 `float` 存 `1700.0`，源文本为 `1700`。比对前须做整数化归一。

核验结果落 `data/verification.json`，含通过项数、未通过明细、未通过定性。

### 步骤 9 生成数据层与站点

**数据层**：台账 CSV 用 `utf-8-sig`（Excel 双击直开不乱码）；同时输出 JSON 供程序消费。汇总值一律标注「本知识库计算」，与原文直取值分区呈现。

**勾稽**（可得则必做）：明细表逐行求和等于表头声明值；逐行数量之和等于总计行；子项之和小于等于主项；日期与文件修改时间对照；证号前缀与主体注册地自洽。

**站点层**：单文件 HTML，内嵌数据与极简 Markdown 渲染器（标题、表格、列表、引用、代码块、粗体、页内双链转锚点）。

- 语义标记 `[[类型:值]]` 按类型着色，类型集：金额／单位／标段／人员／日期／证件号／里程／面积／尺寸。末位「尺寸」用于位图规格一类记述。全篇同名，便于 RAG 召回与视觉扫读。
- **中文场景配色遵循涨红跌绿**；红用于金额，绿用于单位与里程，紫用于标段。
- 主题跟随 IDE。浅色主题下所有面板浅底深字。
- 渲染器写完必须跑一次回归测试：从 HTML 中抽出脚本 `node --check` 语法检查，再用 `site_pages.json` 逐页调用渲染函数，断言每页恰好 1 个 h1、表格标签配对、语义标记与粗体均已解析。**断言里要连关键值一起查**（金额、编号、单位名、证书序列号），防止数据内嵌时被静默丢字段。

## 四、常见坑

| 坑 | 后果 | 规避 |
|---|---|---|
| 对带文本层的电子公文盲目跑 OCR | 把干净文本层降级成一堆识别错误 | 第一步判页均字符数，`> 200` 且文本干净则直取 |
| 把扫描件的字符数判据反过来用 | `get_text()` 返回空串，白跑一轮 | 先看字符数再选路线，两条路线不要混 |
| 用 `get_images()` 找电子印章与签章时间戳 | 返回空，误判为「这份没盖章」 | 两者在注释 `/AP` 外观流内；遍历 xref 找 `/Subtype /Image`，或看 `get_image_info(xrefs=True)` 中 `xref=0` 的条目 |
| `/Reason` 当 ASCII 读 | 得到乱码 | 十六进制 UTF-16BE 解码，并 `lstrip("\ufeff")` 去 BOM |
| 印章位图低分辨率硬放大 | 白费功夫，信息上限在源位图 | 先算有效 dpi（位图像素 ÷ 签名域 pt），再定是否值得辨读 |
| 印章展开图过宽 | 被渲染端压缩到不可辨 | 宽 1100 至 1600 px；实测 6048×270 全糊，1500×300 可读 |
| 展开方向未做四取向比对 | 通篇镜像字，误判为无法辨读 | `flipud × fliplr` 四份都生成，挑可读者 |
| 反向核验不按数值性质分类 | 满屏假阳性（本案报到 18 项） | 内容类溯源文本层，取证类溯源对象路径，分开核 |
| 把未中标通知书缺收件人/日期当作缺陷 | 静默补全，失去保真 | 记为「原件特征」照录，注明取值来源 |
| 断言「证书解析通过」即签名有效 | 越界结论，法务风险 | 写明未做密码学验证，指向文书自带官方验证渠道 |
| 脚本命名为 `inspect.py`、`json.py` 等标准库名 | 循环导入报错，`fitz` 无 `open` 属性 | 脚本名加前缀，如 `probe01.py` |
| 用 heredoc 写含引号的复杂脚本 | shell 提前截断，脚本残缺报 EOF | 复杂脚本改用文件写入工具 |
| 循环变量与业务变量同名（`for b in ...` 与蓝色通道 `b`） | `numpy` 类型错误 | 色彩通道用 `R,G,B` 大写；条目用 `base` |
| 聚类容差用固定像素 | 字号变化处误拆行 | 容差随行高自适应 |
| 复核长卷过宽或过高 | 渲染压缩，小字号不可辨 | 宽 1100 至 1600 px，分张控制高度 |
| 印章环带半径凭猜 | 展开图文字被切 | 按径向红墨密度直方图定环带 |
| 印章读出的名称当作原文事实 | 主体识别失去可追溯性 | 标注来源为印文，进存疑清单 |
| 只做正向核验 | 漏收值不会被发现 | 必须补反向核验 |
| 核验用 `%g` 格式化 | 精度截断，满屏假阳性 | 用完整精度字符串比对 |
| 交付值与计算值混排 | 数字失控，造价文件不可用 | 汇总值单列并标「本知识库计算」 |
| 未记录分歧副本 | 后续无法裁定 | 分歧值与各自来源、置信度全部落盘 |

## 五、复现命令骨架

```bash
PY="C:/Users/<USER>/.workbuddy/binaries/python/envs/ocr/Scripts/python.exe"
# A 纯扫描件路线
$PY ocr_all.py      # 渲染 200dpi 位图 + 逐页 OCR（带坐标）→ ocr_raw.json
$PY layout.py       # 版面还原 → txt/
$PY extract.py      # 字段抽取 + 多副本分歧检测
# B 带文本层电子公文路线
$PY extract.py      # 文本层逐行 + 注释层 + 签名层（含证书链）抽取
$PY stamp_ocr.py    # 签章时间戳位图 OCR + 整页留档
$PY seal_read.py    # 印章红墨掩膜 + 极坐标四取向展开
# 两条路线共用
$PY build_data.py   # 数据层
$PY build_wiki.py   # 文档层
$PY build_site.py   # 站点层
$PY regress.py      # 站点语法检查 + 逐页渲染断言
$PY verify.py       # 双向核验 → data/verification.json
```

环境：需 `pymupdf`、`rapidocr_onnxruntime`、`cryptography`，建议放在同一虚拟环境（用户本机为 `envs/ocr`）。
